# mid-net foundation: from two packets to a game-ready netcode layer

**Status:** design + the first piece built (`bits.rs`, below). Written to be argued with: the decisions that need the owner are at the end.

## Where mid-net is, and what "game ready" means here
Today mid-net moves two hand-written packets (`PlayerState`, `PlayerEvent`) over a `Transport` (a datagram channel and reliable streams, over QUIC/WebTransport). The game that uses it first, Tower of Babylon (C99), has already built its own protocol in C on top of the byte transport: `Hello/Welcome/Input/Snapshot/Disconnect`, a 30 Hz server, client prediction with server reconciliation for movement, and now lag compensation. That work is the proof of what the layer must do; this document is about moving the general parts into mid-net so every game (the Rust engine's, and any C game over the FFI) gets them, instead of every game re-writing them.

"Game ready" is these seven things, in the order they are needed:

| | What | Today |
|---|---|---|
| 1 | Pack fields into bits (bool = 1 bit, health = 7, a position = 17 quantised): the budget is 7.8 ms and about a kilobyte per tick; and let a struct describe its own wire form once (Unity's `INetworkSerializable` / `INetworkSerializeByMemcpy`) | **done: `mid-net-wire::bits` and `::stream`** |
| 2 | Typed **messages** with an id, a channel and a codec; many per packet; a dispatcher | two fixed packets |
| 3 | **RPCs**: a message with a target (server, one client, the owner, all, all but one, a team), a reliability, an authority check, a rate limit, optionally a reply | none |
| 4 | **Network variables / replicated state**: entities with typed fields; the server sends only what changed since what each client last acknowledged; spawn and despawn; interest filtering | none (the game's C snapshot is hand-written) |
| 5 | **Prediction toolkit**: command history, replay from the server's answer, a fading correction; a **rewind buffer** for lag compensation | in the game's C only |
| 6 | **Session**: handshake with a schema check, keepalive, time sync, timeouts that can be told apart ("no signal" before "lost"), clear disconnect reasons | **done: `mid-net::session`** (the game's C still drops everyone at the first 5 s of silence) |
| 7 | **Schema + codegen** from `.mdix`: one description, generated Rust and C with identical bytes, and a schema hash in the handshake so two builds that disagree refuse each other instead of misreading | hand-kept `packets/*.mdix` |

## The shape
Everything above the transport is built from the bottom up, each layer usable alone (the `wire` crate's rule: zero dependencies, no platform assumptions).

* **`mid-net-wire`** (exists): `Sequence`/`AckTracker`, the two packets, and now `bits` (see below).
* **message layer** (new, 2): `MsgId(u16)`, a `Channel` (`UnreliableSequenced`: state, stale ones dropped; `UnreliableUnordered`: cosmetic; `ReliableOrdered`: events; each channel its own sequence space, never one global one, as `mid-net.md` already decided), a `Message` trait (`ID`, `CHANNEL`, `encode(&self, &mut BitWriter)`, `decode(&mut BitReader)`), packets that batch messages up to the MTU, a dispatcher that is a table from id to handler. A backpressure rule on the reliable queue (a cap, and what happens past it: drop the connection, never grow without limit: Unreal's documented failure).
* **RPC layer** (3): an RPC is a message plus `Target`, `Delivery`, an `allow(sender, rpc) -> bool` hook the server runs before anything executes, a per-rpc and per-sender rate limit, and execution **queued to the start of the next tick** (never inline from the packet handler) so the order is the same on every machine. Request/response is a pair of messages with a correlation id and a timeout. A client can only call RPCs marked client-callable, and a server-to-client RPC that arrives at the server is dropped and counted.
* **replication layer** (4): `EntityId`, an entity *kind* (a list of fields: type, bits, range, interpolation mode, who may write it), per-client baselines (the last server tick the client acknowledged), a **dirty mask** per entity (a bit per field changed since the baseline) written ahead of only the changed fields, spawn and despawn on the reliable channel with the first full state, and an **interest filter** (a predicate per client: team, room, distance) deciding who gets which entity. The client keeps a short interpolation buffer per entity and fires an `on_change` per field. A baseline older than the server keeps (about 2 s) falls back to a full state.
* **prediction toolkit** (5): generic `CommandHistory<Cmd, State>` and `Reconciler` (re-run from the server's state with the unacknowledged commands, report the error, feed a fading offset) and `RewindBuffer<T>` (the last N ticks of poses, `at(tick)`, `at_f(tick)`, a clamp on how far back anyone may ask). Ported from the game's tested C (`net_client.c`, `net_history.c`), with the same tests.
* **session layer** (6): version + **schema hash** in the handshake, a keepalive so an idle link is told from a dead one, round-trip and server-tick estimation, a state machine `Connecting → Connected → NoSignal(since) → Lost(reason)` so a game can show "NO SIGNAL 3 s" and reconnect instead of dropping at the first 5 s gap.
* **codegen** (7): `tools/mdix-compiler` (the only place `dixscript` is allowed, by policy) reads `.mdix` schema files and writes plain Rust and plain C: message structs, their `encode/decode`, RPC send/dispatch stubs, replicated-entity structs with the dirty-mask delta codec, and the schema hash. The generated code is checked in, so the core crates stay free of `dixscript` and of reflection, and a C game compiles the same bytes with no Rust in its build.

## What exists now: `bits.rs` (layer 1)
`BitWriter` over a caller-owned slice (no allocation), `BitReader` over borrowed bytes. Fields: `bits(1..=64)`, `bool`, `u8/u16/u32/u64`, raw `f32`, `varint` (LEB128, bit-wise), `zigzag`, **quantised float** (`min..=max` in 1 to 32 bits, error at most half a step), **octahedral unit vector** (`2 * bits`, 2 to 16), byte-aligned `bytes`, `str` with a length limit. **The packing is a contract** other languages must reproduce: least significant bit first, golden vectors pinned in the tests (`write_bits(0b101,3)` then `write_bool(true)` is `0b0000_1101`; varint 300 is `AC 02`; a quantised 0.5 in `0..1` at 8 bits is `0x80`, half rounded away from zero). **No input can panic it** (20 000 random buffers with random reads in the tests); every write that does not fit, and every read past the end, is an `Err`, and a failed write changes nothing. NaN and infinity are refused rather than turned into a number; a finite value outside a range is clamped to it. **Tests:** 15 new (40 in the crate; the 15 include a 3000-round random mix of every kind of field, every width at every bit offset, and the hostile-input run), 16 mutations caught (packing order, continuation bit, zigzag, rounding, clamping, varint limits, octahedral fold, range checks, atomic writes and reads, length overflow, string limits, NaN).

## Structs and traits over the net (layer 1, second part: `stream.rs`, built)
Primitives are easy; the question is a struct (a `Hit`, a `PlayerState`, an inventory) and a trait. Unity answers with two interfaces; this layer answers with the same two and one more, in the engine's usual shape (declarative macros, no procedural macro, no dependency, Rust 1.75):

| Unity netcode | here | what it is |
|---|---|---|
| `INetworkSerializable` + `BufferSerializer<T>` | **`NetSerialize` + `BitStream`** | a type writes **one** function that visits its fields through a stream that is either writing or reading, so the writer and the reader are the same code and a field cannot be written in one order and read in another |
| `INetworkSerializeByMemcpy` | **`NetPod`** + `write_pod`/`read_pod` | `#[repr(C)]` plain data copied as its bytes (little-endian only); `impl_net_pod!` fails to compile if the struct has padding (a doc test shows it); bigger than the packed form, no description needed |
| `NetworkVariable<T>` | layer 4 (replication) | later |
| a polymorphic message / `INetworkMessage` | **both honest ways, built (`poly.rs`)**: `impl_net_enum!` (a tag, then the variant) and `MessageRegistry` / `Dispatcher` (a message id, then the type's fields) | **a trait object cannot cross a network**: the other end has no idea what it is, so what travels is *which one it is, then its fields* |

`impl_net_serialize!(Hit { target: bits(10), damage: quant(0.0, 500.0, 12), dir: unit(12), crit: flag(), note: string(16) })` writes the function from a field list; the field kinds are `flag`, `bits(n)`, `sbits(n)`, `varint`, `quant(min,max,bits)`, `unit(bits)`, `string(max)`, `list(max)`, and `raw` (a full-width number, a nested struct, an array, an `Option`). Lists and strings carry a limit the caller chooses, checked on both sides, and **reading a list never allocates more than the packet can hold** (a claimed length bigger than the bits left is refused before anything is allocated: a 5-byte packet cannot ask for 4 GB). `net_round_trip` makes a value exactly what the other end will read (quantised fields lose their extra precision), which is what a sender needs to run its own simulation from the rounded value, as the game's prediction does with its commands.
**Tests:** 13 unit tests and 3 doc tests (one is the `compile_fail` for padding): one description writing and reading a struct with every kind of field, pinned bytes, reading over a dirty struct, signed fields at their edges, widths and varints that do not fit the type, list and string limits, the allocation claim, `Option`, the round trip, plain data (little-endian bytes, unaligned start, every bit pattern valid, short packets), and 30 000 random packets that must neither panic nor allocate wildly; 14 mutations all caught (13 by tests, 1 by the compiler). **Compiled and tested on Rust 1.75 (the workspace floor) and on current stable; clippy is clean.**

### The two ways to send "one of several types" (`poly.rs`, built)
**1. An enum** (`impl_net_enum!(Command, 3, { Move { dir: unit(12), sprint: flag() } = 0, Fire { weapon: bits(4) } = 1, Stop {} = 2 })`): the variants are a closed list known to both ends at compile time; the wire form is a tag of the width you give (2 bits for 4 variants), then that variant's fields with the same field kinds as a struct. Variants are written struct-style (`Stop {}` has no fields); every variant has a literal tag; reading builds the variant from `Default` and reads its fields in, and an unknown tag is `BitError::UnknownTag` (never a panic, never the first variant by accident). A tag that does not fit the width is refused on writing. Enums nest in structs and lists (`raw()`, `list(n)`). A new variant is a new protocol version.
**2. A message id and a decoder table**, for an open set of types (the messages and RPCs of a whole protocol, each module registering its own): a type implements `NetMessageType` (its `NetSerialize` fields, `Default`, and a `const ID: u16`); a message on the wire is the id in the table's width (1 to 16 bits; 8 gives 256 types in a byte) then the fields.
* `MessageRegistry` reads back a `Box<dyn NetMessage>`: to inspect, log, forward or queue a message without knowing its type; `downcast_ref::<T>()` / `downcast::<T>()` get the type back (and say so if it is another one). Writing a message that is not registered is refused (the other end could not read it) and writes nothing.
* `Dispatcher<C>` calls a **typed handler per id** (`d.on::<Hit>(|world, hit| ...)`) with a context: decoding is into a value on the stack (no allocation per message), and **a handler runs only after its whole message was read without error**, so garbage never reaches game code. Registering a duplicate id, an id that does not fit the width, or a bad width is refused.
* **Opaque messages** (`RawMessage`, `MessageRegistry::register_raw(id)`): an id registered as raw reads back as `RawMessage { id, data }`; on the wire it is the id, a varint length (at most 65 535) and the bytes, byte-aligned. This is what lets a program with no Rust types (a C game with its own packing) use the same registry, framing and driver: the receiver can find the end of a message it cannot read because the message says how long it is. The price against a typed message is the length (1 to 3 bytes) and up to 7 bits of padding. A claimed length longer than what is left is an error before anything is allocated. `dyn NetMessage` has `as_raw()` / `into_raw()`.
* `write_message(&mut msg, id_bits, &mut writer)` writes one the way both read it. A packet that carries several messages needs a count or a length in front of them; that is the message layer's job (next), not this one's.
**Decisions taken (change any of them):** ids are fixed numbers the schema assigns (never hash or order dependent); the id width is a parameter of the table, not hard-wired; there is no length prefix per message, so an unknown id means the packet is dropped (two builds that disagree are refused at the handshake by the schema hash instead of limping along).
**Tests:** 13 new unit tests and 1 doc test: every variant round trips, pinned bytes (the tag's cost, a string after a tag, a message's id then a little-endian field), reading over a different variant, unknown tags, a tag too wide for its field, nesting; a registry carrying two messages in one packet and handing back the right types, every refusal (duplicate, too large, bad width, unregistered, unknown id, short packet), the id width the same on writing, reading and dispatching at 4, 8 and 16 bits, handlers that keep state, handlers that must not run for a partly read message, and 30 000 random packets that must neither panic nor run a handler on garbage; 13 mutations all caught. Rust 1.75 and current stable; clippy clean.

## Layer 2: channels and packets (`frame.rs`, built; the socket glue is next)
Pure bytes, no socket: the facade will put these over a `Transport`. Two wires, two formats.
**Datagrams** (unreliable): `packet = seq:16 | count:8 | message*`, `message = channel (the table's width) | message id | fields`. The sequence is **per packet**, not per message, so a packet costs 3 bytes of header however many messages it carries (up to 255). `DatagramBuilder` fills a buffer the caller owns (its length is the packet budget, an MTU of about 1200): `push` returns `Ok(true)` added, `Ok(false)` does not fit (the packet is **byte-for-byte as it was**: a message that fails halfway is rolled back with `BitWriter::truncate_to`, so the next, smaller message lands on clean bits), or `Err` for something that can never go in a datagram (an undefined channel, a reliable channel, an unregistered type, a value that does not fit its field).
Channels say what they promise: `UnreliableSequenced` (state: **a message arriving after a newer packet's on the same channel is dropped**), `UnreliableUnordered` (cosmetic events: each message delivered once, in any order), `ReliableOrdered` (a stream only, never in a datagram). `DatagramReceiver` remembers the last 64 packet sequence numbers: **a packet seen twice is dropped whole**, as is one more than 64 behind (too old to tell a repeat from a new one); sequence numbers wrap around correctly (tested across 65535 to 0). `receive` reads the whole packet and only then hands the messages over, so **a malformed packet delivers nothing and leaves the receiver exactly as it was** (a test caught the first version leaving the sequence number marked seen when a packet was cut after its header; every cut position is now tested); `receive_dispatch` runs typed handlers with no allocation as it reads (a stale message is still read to the end and skipped, so the ones after it in the packet arrive), at the price that a malformed packet may have delivered the messages before the bad one: on `Err` the sender is broken or hostile and the connection should be dropped.
**Reliable streams** (a byte pipe, arbitrary pieces): `frame = length (varint, bytes) | message id | fields`. `StreamWriter` queues frames with **two hard limits** (`max_bytes` waiting unsent, `max_frame` for one message): past the first a push returns `Full` and queues nothing, and **the caller must drop the connection**, because a reliable queue that may grow without bound is how one slow peer takes a server down (the Unreal failure `mid-net.md` already names); `fill(out)` hands the transport as many bytes as it takes (a frame may be cut across two calls). `StreamReader` cuts whole messages out of whatever arrives, byte by byte or in pieces: a frame that **claims** more than `max_frame` is refused before anything is buffered, the buffer is capped, a malformed frame (unknown id, trailing bytes) is skipped and the next one still reads, and a wrong length (the stream can no longer be cut up) clears the buffer and errors.
**Decisions taken (change any of them):** the sequence is per packet; a duplicate packet is dropped whole (so an unordered message cannot arrive twice from a network duplicate); no per-message length in a datagram (a decode error drops the rest of the packet, since there is no way to resynchronise); the count is one byte (255); channel ids are 1 to 8 bits; ids and widths are the caller's. **Not here:** acknowledgements and retransmission for unreliable transports (the `reliable` crate does that for UDP; QUIC does it for streams), fragmentation (a message that does not fit an MTU goes on a stream). The glue to a `Transport`, priorities and the per-tick byte budget are layer 4 below.
**Tests:** 19 in `frame.rs` and 1 in `bits.rs`: a packet's pinned header, a message that does not fit leaving the packet identical (compared byte for byte), every refusal, the 255 limit, the channel table's limits, stale versus late events, duplicates and the 64-packet window, sequence wraparound, a malformed packet cut at every position and with a bad channel, a reliable channel or an unknown id (each carrying an otherwise valid message), typed handlers with a skipped stale message, **a simulated network** (six seeds with up to 40% loss, 40% duplication and reordering over 5000 packets across the sequence wrap: no state older than one already delivered ever got through, no event arrived twice, a clean network lost nothing), 30 000 random datagrams, streams cut into random pieces and byte by byte, the full queue and its recovery, over-large claims, malformed frames skipped, handlers not run for a bad frame, 3000 random streams; **19 mutations all caught**. Rust 1.75 and current stable; clippy clean.

## Layer 3: the session (`mid-net/src/session.rs`, built; it answers the drop-after-a-while)
A `Session` is a state machine driven by the clock the caller gives it and by what arrives, and it never touches a transport, so every behaviour below is tested deterministically with a fake network (its own delays, jitter, loss, outages, and a server clock that is a million milliseconds ahead of the client's).
* **Handshake.** The client sends `Hello` (the layer's protocol version, the **schema hash**, a nonce, a name) and sends it again every `hello_retry_ms` until answered (0 turns retries off, right for a reliable stream); the server answers `Welcome` (session id, its clock, the tick rate) or `Reject` (`VersionMismatch`, `SchemaMismatch`, ...). **Two builds that disagree about the messages are told so and never exchange one**, instead of misreading each other (this replaces bumping a protocol number by hand and hoping both phones were rebuilt). A repeated hello with the same nonce gets the same welcome again; a different nonce on a live session is a protocol error. The nonce stops a welcome or reject meant for another hello from being believed.
* **Keepalive and time.** The connected client pings every `ping_interval_ms`; the server answers with its own clock. That is both directions of "I am still here", a smoothed round-trip time (the reliable crate's estimator), and a **clock estimate**: the offset to the server's clock comes from the sample with the **lowest** round trip of the last eight, because it was the least delayed; the error of one sample is half the difference between the outward and the return delay (tested: 30 ms out and 50 ms back gives an estimate within 10 ms; with up to 100 ms of one-sided jitter and 10% loss the estimate was never off by more than 30 ms over minutes, where choosing the slowest sample, or only the newest, gave up to 50).
* **No signal is not lost.** Silence for `no_signal_ms` (default 1.5 s) turns `Connected` into `NoSignal` and fires an event, so the game can show "NO SIGNAL"; anything heard (`on_packet_received` for **any** datagram or stream bytes, not only control messages) turns it back with `Recovered { gap_ms }`; only silence for `timeout_ms` (default 10 s) ends the session with `Timeout`. The thresholds are exact (tested at one millisecond either side). **The game's old behaviour, dropping everyone at the first 5 s of silence, is one setting of this; a phone whose Wi-Fi sleeps for 6 s now shows NO SIGNAL and comes back.**
* **Ending.** `Ended` says why: `LocalClose`, `PeerClosed(reason)` (a goodbye carries a reason: normal, kicked, full, ...), `Timeout`, `ConnectTimeout`, `Rejected(reason)`, `ProtocolError`. An ended session produces nothing more and ignores everything (a test feeds one random messages for thousands of rounds); closing twice says goodbye once; a clock that steps backwards is ignored (time never goes back inside the session).
* **On the wire** control messages are one enum (`ControlMsg`, message id 0, reserved by the application) through the same registry and framing as everything else: handshake and goodbye on the reliable stream, pings on a datagram; a ping is at most 8 bytes and a pong 12. A test runs a whole connection through `DatagramBuilder`, `DatagramReceiver`, `StreamWriter` and `StreamReader`, the stream cut into pieces of 5 bytes.
**Decisions taken (change any):** the client pings and the server only answers (the server hears the client's pings, the client hears the pongs: both directions are covered with half the traffic); defaults 500 ms ping, 1.5 s no signal, 10 s timeout, 5 s to connect, 500 ms hello retry; the schema hash is a number the code generator writes (`fnv1a64` makes one from any bytes meanwhile); times are `u64` milliseconds on any monotonic clock the caller owns. **Not here yet:** reconnecting a lost session with a token; the server-side rate limit on pings. (The driver that owns a `Transport` and runs this against a clock is layer 4.)
**Tests:** 16: connects and says so, disagreeing builds are rejected (schema, protocol version) and an ended session is silent, hello retries (and none when off, ending in a connect timeout), a handshake that never finishes ends on time on both sides, a retried hello, wrong-nonce welcome and reject ignored, nonsense for a role is a protocol error, a ping before the handshake is not answered, round trip and clock to within the asymmetry (and ping spacing), the least-delayed sample under jitter, **a gap shown then recovered and a long one ending the session** (events and exact times), anything heard is a sign of life with exact timeouts, a clock going backwards, closing and its reason, the messages' sizes and round trips, a whole connection through the framing, 3000 rounds of random messages at random times, and **an hour of simulated play with 3% loss, jitter and 93 outages of up to 6 seconds: never ended, every NO SIGNAL recovered, the clock estimate within 200 ms even across the gaps, then one 60 s outage ends both sides once**; 22 mutations: 21 caught, 1 equivalent (the second guard against ending twice in `end`, which no path can reach, kept as a defence). Rust 1.75 (compiled and tested by hand against the 1.75 compiler) and current stable; clippy clean.

## Layer 4: the driver (`mid-net/src/driver.rs`, `threaded.rs`, `driver_ffi.rs`, `sim.rs`; built)
The glue. A `Driver<T: Transport>` owns a transport, a `Session`, a `DatagramReceiver`, one `StreamWriter`/`StreamReader` per reliable channel and the queues between them, and runs them against a clock the caller passes to `poll(now_ms)`. It never blocks and starts no thread, so it is deterministic and a test replays an exact network.
* **`Schema`** is what both ends must agree on: the `MessageRegistry` and the `ChannelTable`, sealed once (it registers the session's `ControlMsg` under id 0, so the application must not use 0, and checks that the two control channels exist: one reliable, one datagram) and shared by every connection through an `Arc`. `Schema::default_channels(bits)` is a table with channel 0 (reliable) and 1 (unordered datagrams) already the session's.
* **Channels map to transport streams one to one:** each reliable channel is its own stream (stream id = channel id), so a stalled message on one channel cannot hold back another, and each keeps its own order. A datagram channel is a channel in a datagram.
* **Priorities and the budget.** `send(channel, priority, msg)` on a datagram channel queues the message; at each flush the queue is sorted by priority (higher first, then first come first served) and packed into datagrams of at most `mtu` (default 1200) until `datagram_budget` bytes have gone out; the rest wait for the next flush. Names for the numbers are in `driver::priority` (COSMETIC 0, LOW 64, NORMAL 128, HIGH 192, CRITICAL 224, MAX 254; 255 is the session's). Strictly in priority order: a message that does not fit ends the packet, it is not skipped for a smaller one. Reliable channels ignore the priority and are flushed (control stream first, then by channel id) up to `reliable_budget` bytes per flush.
* **What is dropped, and how you know.** A datagram message that has waited `datagram_ttl_ms` (default 500) is dropped (a stale state update is worse than none); when the queue holds `max_queued_datagrams` the lowest priority, oldest message goes (an equal-priority newcomer replaces the oldest); both are counted in `DriverStats`. A message that cannot go in a datagram even alone, or cannot be encoded (a NaN in a quantised field), is dropped and reported as a `DriverEvent::Dropped`, because that is a bug in the sender, unlike the two above. The session's own pings are above every priority a game can use, ignore the budget and never expire, so a saturated link never looks dead. After the connection has ended the game's queued messages are not sent.
* **Receiving.** Reliable streams are read first (the handshake travels on one), then datagrams. A message that arrives before the handshake has finished (the streams are independent, so an application message can overtake the welcome) is **held** (at most 256) and released when the session connects, not lost and not shown to the game early. While `max_inbox` messages wait for the game the driver stops reading the transport instead of growing, which pushes back on the peer; one poll reads at most `max_receive_per_poll` times. Anything heard on either path is a sign of life for the session, except a datagram that cannot be parsed.
* **What ends a connection** besides the session's own rules: the transport failing or having been connected and no longer being (`Fault::Transport`, `Fault::TransportClosed`), bytes on a stream the schema does not have (`UnknownStream`: this includes ids that do not fit a byte), a stream carrying something that is not a message (`MalformedStream`) or more than a frame without completing one (`StreamOverflow`), and a reliable queue that fills (`SendQueueFull`, and `send` returns `QueueFull`): the peer is not reading, and waiting would grow memory without bound. Each is reported once as a `DriverEvent::Fault` with the cause, the peer is sent a goodbye (`ProtocolError`) where the transport allows, and the session ends. A garbage datagram is only counted (`bad_datagrams`): the network can deliver those from anywhere.
* **`Router<C>`** calls a typed handler per message id with a context the caller owns (`router.on::<Hit>(|ctx, channel, hit| ...)`, `on_raw(id, ...)`) over the driver's inbox, and hands back what nobody handles.
* **`Server<T>`** is many connections: one `Driver` per client, a shared `Schema`, one inbox and one event queue (each tagged with the `ConnId`, which is also the session id the client is told). *Accepting* a connection is the transport backend's job (a QUIC listener, a relay); `accept(transport, now)` takes what it produced. A full server accepts the connection only to tell the client why (`Rejected(Full)`) and drops it. `broadcast` sends to every connected client except one, `kick(id, reason)` ends one, and connections that ended are forgotten after their `Ended` event is queued.
* **`NetThread`** (`threaded.rs`) is the same driver on a thread of its own, for a program that would rather not call `poll`. The driver and the handler are built **on** the thread (the closure given to `spawn` runs there), so neither has to be `Send`; the thread polls every `tick`, hands each received message to the handler (on the net thread: forward it however the game likes), passes events back through `next_event`, and takes messages to send (which must be `Send`) through `send`. A message the driver refuses comes back as `DriverEvent::SendRejected`. Dropping it says goodbye and joins.
* **`sim.rs`** is a simulated network that implements `Transport`: loss, duplication, delay and jitter (which reorders), an MTU, reliable bytes cut into random pieces, outages (datagrams lost, reliable bytes held), a cut link, a link that connects late; a clock the test sets and a seeded generator, so a run is the same run every time. It is public because a game can use it for a "lag switch" in a test build.
* **The C ABI** (`driver_ffi.rs`, header `ffi-smoke-test/mid_net_driver.h`): the transport is **five C callbacks** (shaped like the QUIC backend's own C functions, so it plugs in with a thin adapter); a schema is built from C (`mid_net_schema_new/channel/message/seal`; a sealed schema may be freed while drivers made from it live); a driver (`mid_net_driver_client/server_end`) or a server (`mid_net_server_*`) is an opaque handle; messages are `(channel, priority, id, bytes)` in and out, the bytes being the program's own packing, carried as `RawMessage`s; events and a state snapshot are flat `#[repr(C)]` structs. `next_message` with a buffer too small returns `-2` and leaves the message queued with its size in `*len`. Every function checks its pointers and cannot unwind across the boundary. **Typed, bit-packed messages stay on the Rust side until generated code and a descriptor interpreter exist** (decision 1 below); until then a C game pays the length byte or two. The header is hand-written and a Rust test reads it and checks every number against the Rust enums, so the two cannot drift.
**Decisions taken (change any):** single-threaded `poll` is the core and the thread is a wrapper (you asked for both); the inbox of boxed messages plus an optional `Router` rather than a `Dispatcher` inside the driver (the C ABI and the thread both need boxed messages; the streaming `Dispatcher` stays available on the layer below); strict priority order; the control channels are numbered by the schema; time is `u64` milliseconds on any monotonic clock the caller owns, and a clock that steps backwards is ignored. **Not here yet:** fragmentation, reconnecting with a token, per-sender rate limits on a server, a typed C interface.
**Tests:** 11 in `sim.rs`, 65 for the driver, server and router, 6 for the thread (real time, generous deadlines), 9 for the C ABI, and a real C program (`ffi-smoke-test/driver_test.c`, 92 checks) that drives a client, a server end and a multi-client server over a transport **implemented in C**; 8 new in `poly.rs`. The driver tests include: the handshake over a perfect and a late-connecting link; reliable messages once and in order through 30% datagram loss, 10% duplication, jitter and 7-byte stream pieces (1500 per channel on two channels); a sequenced channel never going backwards under reordering; priority order, equal priorities in order, the clamp at 254, a flood of critical messages that cannot starve the keepalive (the datagram count proves the pings went out); packets filling to the mtu and never past it; the budget limiting each flush, and a packet that **exactly** spends it still going; the ttl to the millisecond; the full queue's choice of victim; NO SIGNAL shown, sending still accepted during it, then recovered with the reliable message arriving after; a long outage timing out both ends; **half an hour at 30 Hz with 5% loss and 90 outages: never ended, every reliable message once and in order**; a goodbye through a saturated stream; the app's own traffic keeping a connection alive without any ping; hostile bytes (random datagrams, corrupted real packets and streams, garbage frames, an unknown stream including 260, an endless frame); a cut transport and one that errors (one fault, not one per call); a message held until the handshake and a flood of them capped; the inbox's exact limit; the same seed giving the same run. **Mutations:** 99 single-line changes to `driver.rs` (every comparison boundary, every stat, every limit, the sort orders, the guards): 97 caught, 2 equivalent (a redundant `is_ended` guard, and the re-queue order, which the next flush's sort makes unobservable); 41 changes to `driver_ffi.rs`: all caught, by the Rust tests or the C program. ## Independence, and what mid-math's FFI teaches
mid-net must stand on its own: it serves this engine and any other game, in any language. So the core crates keep their rule (zero dependencies, no platform assumptions, nothing from the engine), and anything that joins mid-net to another engine crate is a **bridge** the user opts into, as `mid-reflect` already does with its `math` feature and `mid-math` does with `mint` and `ffi`. Neither side depends on the other.
`mid-math`'s C ABI (`ffi/`, off by default, 1 300+ `extern "C"` functions) is the pattern to follow, and it shows three things that carry over:
* **Small plain data crosses as a `#[repr(C)]` value struct** (`CVec3`, `CQuat`), and **compressed storage types cross as their raw bits**: `f16`/`bf16` as `u16`, `F8Norm` and the 8-bit floats as `u8`, `BitMask8..64` as the integer, `BitMask128/256` as `[u64; 2]` / `[u64; 4]`. Those storage types are exactly what a network field is ("store compressed, unpack only to compute"): `f16`/`bf16` for velocities and angles, `F8Norm` for 0..1 values, the deterministic `Fixed8/12/16` for positions, and **`BitMask`s are the natural dirty masks and interest sets** of the replication layer.
* **Arrays cross as pointer + length** (its `wide_batch` functions): the same shape as a packet buffer.
* **Stateful things need an opaque handle** (mid-math has none because it is stateless; mid-net's QUIC FFI already uses handles for connections), and everything a C caller must free has one named free function.
So the plan is: a small `mid-net-math` **bridge crate** (depends on both) that implements `NetSerialize` for the mid-math types that make sense (vectors, quaternions, the storage types, bit masks), so the Rust engine writes `pos: raw()` and gets a quantised or packed form; mid-net itself defines the half-float and fixed-point wire forms only as IEEE-754 binary16 bits and plain integers, which any language can read without mid-math.

## What a C (or any other) game uses
The contract is **data, not Rust**: a *schema* (messages, RPCs, entity kinds, with every field's kind, bits and range) written once in `.mdix`. From it the generator writes: (a) plain Rust and plain C source with the typed structs and their encode/decode, byte-identical by the packing contract in `bits.rs`, and (b) the same schema as a small **descriptor table** (an array of field descriptors: kind, bits, min, max) plus its **hash**, which the handshake compares so two builds that disagree refuse each other. A game in another language can read the descriptor table with a few hundred lines of its own, or call the Rust interpreter through the C ABI; nothing requires Rust at run time. That settles decision 1 below. **Today** (layer 4) a C game already runs the whole driver and server through the C ABI with opaque messages (an id and its own bytes); the generated typed structs and the descriptor interpreter are what make those bytes bit-packed instead of byte-aligned.

## How this meets Tower of Babylon (the use cases that drive the API)
The game's next features are exactly the layers above, so they are the first customers and decide the shape:
* **Pick up, drop, swap, use an item** (players start with only hands; items are carried and dropped by everyone) = **RPCs** from client to server (`PickUp(item)`, `Drop(slot)`, `Use(slot)`), with an authority check (reach, ownership, is it still there) and a reply or a correction.
* **An item lying on the floor, a monster, a door** = **replicated entities**: spawned by the server with their full state, then only their changes.
* **Health, ammo, the held slot, the team** = **network variables**: owner-only or everyone, quantised (health in 7 bits, ammo in 6), with `on_change` to drive the HUD.
* **Teams** (players hurt each other except teammates) = a field on the player entity, an **interest and target filter** (`ToTeam`), and a rule in the server's damage code; mid-net provides the group and the filter, the game decides what friendly fire means.
* **Shooting** = the fire bit in the command, the seed derived on both ends, the rewind buffer for the hit check (`net_shots.md` in the game repo).

## Decisions for the owner
1. **Settled by the independence rule, pending the owner's word:** the contract is the **schema** (`.mdix`) and its **descriptor table + hash**; generated Rust and C is the default path (no registry, no reflection, a C game links only the transport and compiles the same bytes); the Rust interpreter behind the C ABI is an optional convenience for a language that would rather not generate code. Nothing at run time requires Rust.
2. **Tick rate:** the doc's budget says 128 Hz, the game runs 30 Hz. The layer should be tick-agnostic (the tick is a number the caller advances); is 128 Hz a real target for the Rust engine or a ceiling?
3. **ECS:** should replication in the Rust engine be defined on `mid-ecs` components (the schema's entity kind maps to a component set) from the start, or stay a plain entity table the ECS adapts to later?
4. **Teams:** a generic `Group` (id, members) in mid-net with filters on it, and teams as one use of it (recommended), or teams only in the game?
5. **Authority model:** server-authoritative for everything except what an owner predicts (their own movement, their own held item), as in the game now; is there any case you want client-authority (cosmetic physics, a car)?
